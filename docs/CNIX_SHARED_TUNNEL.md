# CNIX 共享隧道：使用与维护

这是开发分支的功能说明。本次没有发布版本、部署面板、创建 CNIX 映射或迁移旧线路。面板与两端 Agent 必须使用本分支构建的程序。仓库当前的 2.63.0 版本标签不代表已发布的 2.63.0 Agent 含有此功能，后台通过 `CnixCapabilities` 检查实际能力，旧 Agent 会被明确拒绝。

## 创建一次，以后复用

1. 打开「隧道组建」，新建隧道，名称填写「CNIX共享隧道」。选择「隧道转发」，打开「CNIX共享隧道」开关。
2. 只选国内入口和野草云出口两个节点。传输协议固定为 relay/TLS；首版只支持 TCP 业务，IPv4 入口和 IPv4/域名落地，不支持 UDP、TCP+UDP、多跳或混合线路调度。
3. 选择一个独立的出口本机服务端口，或留空由端口账本自动分配。先不填写外部加速入口也能创建出口。列表会显示「出口映射目标：出口 IP:本机端口」和待映射状态。
4. 在 CNIX 控制台创建一条**新的专用映射**，将新加速入口映射到刚显示的野草云 IP:端口。放行对应云防火墙，检查 CNIX 供应商的国内服务器白名单。面板没有自动修改 CNIX 账户或云安全组。
5. 编辑这条隧道，补录 CNIX 实际给出的外部 `IPv4/域名:端口`。外部端口与本机服务端口可以不同。已有业务时禁止直接修改这两个端点，避免一次修改中断所有业务；需要另建隧道后逐业务迁移。
6. 到「转发管理」创建 A/B/C。每条填写自己的名称、国内入口端口和落地 `IP/域名:端口`，都选择刚创建的共享隧道。每条业务不再创建出口监听端口，也不再需要新增 CNIX 映射。
7. 使用转发诊断检查经 CNIX 的 TLS 身份、relay 认证与目标 TCP 连接。只有经过完整检查的连接才报告已验证；节点在线、服务端口可连接、表单保存成功都不能替代这一检查。卡片显示最近一次检查结果，业务目标的当前状态由转发健康检查提供。

客户端保留原落地协议、UUID/密码、REALITY 公钥、short ID、SNI、flow 等信息，只将访问地址和端口改为对应国内业务入口。不要在客户端填写共享隧道密码。面板生成隧道种子，为各业务派生不同的凭据，自动下发至国内 Agent。

```text
客户端 A → 国内端口 A ─┐
客户端 B → 国内端口 B ─┼→ 同一个 CNIX 外部端口 X → 野草云共享端口 Y
客户端 C → 国内端口 C ─┘                           → 按 relay 请求连接各自落地
```

当前旧线路的 CNIX 17148、野草云 443/12001、出口转发 87 不属于本功能创建的资源。本次不得覆盖这些端点，也不得将旧 nftables 原始业务数据直接接到共享 relay 端口。

## 暂停、删除、额度和限速

- 暂停 B：暂停 B 的国内 TCP 服务并撤销 B 的出口凭据，断开 B 已有会话；不停止共享监听，也不关闭 A/C 会话。恢复 B 时重新启用其授权。
- 删除 B：只删除 B 的入口、chain 和授权。A/C 的目标不改，共享出口仍在。共享业务不允许仅删除数据库记录的“强制删除”。
- 已暂停的共享业务编辑后仍保持暂停状态。
- 删除共享隧道：后台先检查业务引用；仍有业务时拒绝删除。移除用户隧道权限时先撤销该用户的共享凭据，保留其他用户业务。用户自建共享隧道仍有业务时不能直接删除用户。
- 业务流量复用国内入口的现有计量和账单通路。出口 `cnixshared-<隧道ID>` 的总流量不是普通业务服务名，不能再次计入客户额度。原有单向/双向计费和倍率规则保留。
- 流量额度沿用已有用户套餐或用户隧道授权额度，按授权主体累计；本次没有额外新增每个 Forward 的独立流量套餐。达到额度或到期时，原有流程会按业务暂停，并撤销相应共享凭据。
- 已分配的限速规则在每个共享业务入口使用独立的速率桶，同一规则的 A/B 不抢彼此的业务速率桶。规则更新会更新其业务速率。已有按连接的限制仍保留。

## 认证与恢复

共享出口没有固定 forwarder。仅接受 TCP CONNECT，凭据与请求目标必须同时匹配该业务的授权。BIND、UDP、Unix socket、serial、匿名请求、错误密码、其他业务目标均拒绝。授权到期后，出口会拒绝新连接并关闭到期主体的已有会话。

国内链只包含 CNIX 外部入口，不包含野草云直连或落地直连备用地址；缺少 chain、CNIX 断开、TLS 校验失败、认证失败时都关闭连接。落地域名在出口解析，所有解析结果须为允许的公网 IPv4，并按已经校验的 IP 建连，阻止解析跳转至内网、回环、链路本地、云元数据、CGNAT 和基准测试网络。

每个共享隧道有专用自签证书与专用信任根，使用固定的 `cnix-<隧道ID>.invalid` TLS 身份校验，默认开启 `secure=true`。这不是向公共域名申请的证书，CNIX 外部域名无需与证书名称相同。私钥及认证种子/业务密码在数据库按现有 JWT_SECRET 加密体系保存，普通隧道列表只返回端口、外部地址、状态及错误。JWT_SECRET 变化前必须备份并迁移密文，不能随意替换。

Agent 将配置原子保存为权限 `0600` 的 `gost.json`，其中包含恢复所需的 relay 授权、证书、业务服务和 chain。磁盘写入失败不能返回保存成功。共享凭据热更新失败时恢复上一份有效策略；被此次尝试撤销的会话可能需要重连，其他业务会话不重建。面板定时重新同步共享出口授权，重连时可恢复或重试；相同策略不创建新的监听端口。

证书有效期为三年。首版没有自动证书轮换界面；到期前创建新的共享隧道和映射，逐业务迁移并删除旧资源。不能以跳过 TLS 校验来替代续期。

## 构建、数据库与回退

后端启动时幂等创建 `cnix_shared_relay` 和 `cnix_shared_grant`。也提供 `migrations/20261015_cnix_shared_relay.sql`，不修改现有隧道表和旧线路。新隧道仍使用现有 `Tunnel.type=2`，共享配置保存在独立表中。出口端口写入统一端口账本，并在创建前检查实际监听和跨节点别名的端口冲突。

本地构建示例（仅构建，不部署）：

```sh
cd '/Users/norwayx/Documents/New project/cnix-shared-development/springboot-backend'
JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home mvn package

cd '/Users/norwayx/Documents/New project/cnix-shared-development/vite-frontend'
npm ci
npm run build

cd '/Users/norwayx/Documents/New project/cnix-shared-development/go-gost'
go build -o /tmp/cloudnest-cnix-agent .
# 在目标服务器部署前另行构建相应 Linux 架构。本次不执行安装/升级。
```

回退前先迁移或删除所有共享业务，再删除共享隧道，确认出口服务已移除，然后才能回退两端 Agent 和面板。保留数据库备份及原 JWT_SECRET。新增表可以保留，旧程序不使用它们。不要直接删表释放端口，也不要在运行中的共享服务上盲目换回旧 Agent；兼容认证栅栏会拒绝业务，而旧程序没有完整的目标授权能力。

GitHub 回退基线：标签 `rollback/pre-cnix-shared-20261015` 和分支 `codex/rollback-before-cnix-shared`，均指向 `07b7d4f45c02b575ac6098a46d952befad349158`，与已发布的 `2.63.0` 对应。可以从该标签创建独立恢复分支构建旧代码；不要对包含个人未提交改动的工作区执行强制重置。此基线保存已提交代码，不包含原工作区仍未提交的私有代理修改；那些修改仍保留在原工作区。上线后的数据库、Agent 配置和供应商映射需要按上述顺序单独恢复，Git 回退不会自动撤销它们。

本次没有修改 VERSION/AGENT_VERSION、打版本标签或启动发布流程。仅将独立开发分支推送到用户仓库供代码审查，未合并主分支。开发分支与原工作区隔离，审查后再集成和确定正式版本。
